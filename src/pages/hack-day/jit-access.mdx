# Track 04 · Just-In-Time Access

Standing access is access somebody holds whether they are using it or not. **Just-In-Time access**,
or JIT, replaces it with access that is approved in advance but not provisioned until the person
activates it, then removed automatically when the activation expires.

In this hack you will build one. You create a privileged group in the demo system, teach your
connector to grant and revoke it, put it under your tenant's JIT policy, and request it — ending with
an entitlement you are approved for, that is deliberately not provisioned, sitting on your Launchpad
waiting to be switched on.

**You will need:** a finished [Track 02](/hack-day/saas-connectivity) connector, a terminal, and a
browser.

:::caution Start with Track 02

This track builds on the connector from
[Track 02 · SaaS Connectivity](/hack-day/saas-connectivity). You need its source deployed in your
tenant, with accounts and entitlements aggregated, before step 1 makes sense.

:::

JIT splits one familiar thing into two separate things:

| | What it means | What it is called |
| --- | --- | --- |
| **The assignment** | You are approved for this access. It is yours to turn on. | An **entitlement connection** of type `JIT` |
| **The activation** | The access is switched on now by activating the access in the source | A **JIT activation** on that connection |

Standing access collapses both into one. JIT keeps them apart and is demonstrated in this hack.

## What you are building

```
  create a privileged group  ->  add std:account:update  ->  put it under JIT policy
  in the demo system             to your connector            (step 6)
  (step 1)                       (step 3)
                                                                      |
         request it (step 7) ---> approved, but nothing provisioned
                                                                      |
         see it on Launchpad (step 8) ---> waiting to be activated
                                       |
                                       |
         activate  ---> your connector adds the group
         expire    ---> your connector removes it, with nobody asking
```

### 2. Give yourself an account on the source

The 50 accounts from Track 02 belong to fictional people. JIT access is activated by whoever holds
it, so you need an account on this source that belongs to the identity you are signed in as.

#### Correlate it to the shared identity

An account is a row in the demo system. An identity is the person your tenant governs. **Account
correlation** is the rule connecting the two. Setup the correlation as shown:

In your source, go to **Account Management → Account Correlation** and add a rule:

| Field | Value |
| --- | --- |
| Identity Attribute | `Email` |
| Account Attribute | `email` |

This matches the `developer-relations@sailpoint.com` on your new account against the Email on the
`hack.day` identity. The 50 accounts from Track 02 belong to fictional people, so they match no
identity and stay uncorrelated, but the one you just added will correlate and you will have a real identity correlation.

Save it, then run **Account Management → Account Aggregation → Start Aggregation**.

### 3. Enable provisioning on your connector

JIT does not store access. It calls your connector. Activation sends `std:account:update` with an
`Add` operation, and expiry sends the same command with a `Remove`. Without those commands JIT is not possible.

Your Track 02 connector added reads. Now we will add the writes.

#### Declare the command

Add `std:account:update` to the `commands` array in `connector-spec.json`:

```json
  "commands": [
    "std:test-connection",
    "std:account:list",
    "std:account:read",
    "std:account:update",
    "std:entitlement:list",
    "std:entitlement:read"
  ],
```

The platform only sends commands the spec lists. Until this line exists, the handler below is
unreachable code.

#### Add the membership calls

The demo API treats group membership as its own resource rather than an attribute you overwrite,
which is how most real sources behave. Adding and removing a member are a `PUT` and a `DELETE` on
the same path, and both are idempotent — adding twice reports `changed: false` instead of failing.

In `src/my-client.ts`, add these three methods inside `MyClient`, below `getAllEntitlements()`:

```typescript
    async addEntitlement(accountId: string, entitlementId: string): Promise<any> {
        const response = await this.httpClient.put(`/groups/${entitlementId}/members/${accountId}`)
        return response.data
    }

    async removeEntitlement(accountId: string, entitlementId: string): Promise<any> {
        const response = await this.httpClient.delete(`/groups/${entitlementId}/members/${accountId}`)
        return response.data
    }

    async updateAccount(id: string, updates: Record<string, any>): Promise<any> {
        const response = await this.httpClient.patch(`/users/${id}`, updates)
        return response.data
    }
```

`updateAccount()` uses `PATCH`, which changes only the fields you send. The demo API also has a
`PUT` that replaces the whole account, and anything you omit from a `PUT` body reverts to empty.

#### Write the handler

Chain `.stdAccountUpdate()` onto the same `createConnector()` call in `src/index.ts`. The handler
walks the `changes` array and applies each operation. Three operations can arrive, and `groups`
needs different treatment from an ordinary attribute:

| Operation | On `groups` | On any other attribute |
| --- | --- | --- |
| `Add` | `PUT` each value onto the membership endpoint | Never sent. `Add` only works on multi-valued attributes. |
| `Remove` | `DELETE` each value from the membership endpoint | `PATCH` the attribute to `null` |
| `Set` | `PATCH` `groups` to exactly the values sent, replacing the list | `PATCH` the attribute to the value sent |

One detail to note here. A single value arrives as a bare string and several arrive as an
array, so normalize before you loop.

Paste the handler below and you should be done writing the code.

```typescript
        .stdAccountUpdate(
            async (context: Context, input: StdAccountUpdateInput, res: Response<StdAccountUpdateOutput>) => {
                const id = input.key && 'simple' in input.key ? input.key.simple.id : input.identity
                const attributeUpdates: Record<string, any> = {}

                for (const change of input.changes) {
                    const values = Array.isArray(change.value) ? change.value : [change.value]

                    if (change.attribute === 'groups' && change.op !== AttributeChangeOp.Set) {
                        for (const value of values) {
                            if (change.op === AttributeChangeOp.Add) {
                                await myClient.addEntitlement(id, value)
                                logger.info(`Granted ${value} to ${id}`)
                            } else {
                                await myClient.removeEntitlement(id, value)
                                logger.info(`Revoked ${value} from ${id}`)
                            }
                        }
                    } else if (change.op === AttributeChangeOp.Remove) {
                        attributeUpdates[change.attribute] = null
                    } else {
                        attributeUpdates[change.attribute] = change.value
                    }
                }

                if (Object.keys(attributeUpdates).length > 0) {
                    await myClient.updateAccount(id, attributeUpdates)
                }

                // Read the account back so the platform records what the source actually holds now,
                // rather than what we asked it to hold.
                const account = await myClient.getAccount(id)
                res.send({
                    identity: account.id,
                    uuid: account.id,
                    disabled: !account.active,
                    locked: account.locked,
                    attributes: {
                        id: account.id,
                        userName: account.userName,
                        displayName: account.displayName,
                        firstName: account.firstName,
                        lastName: account.lastName,
                        email: account.email,
                        department: account.department,
                        title: account.title,
                        groups: account.groups,
                    },
                })
            }
        )
```

Add `AttributeChangeOp`, `StdAccountUpdateInput`, and `StdAccountUpdateOutput` to your imports from
`@sailpoint/connector-sdk`. `AttributeChangeOp` is the enum holding `Add`, `Remove`, and `Set`, so
you compare against it rather than against strings.

```bash
npm run pack-zip
sail conn upload -c saas-connectivity-demo -f dist/saas-connectivity-demo-0.1.0.zip
```

You created the connector in Track 02, so this is an upload, not a `sail conn create`. If the zip

#### Turn provisioning on for the source

Uploading the connector is not enough. Before you can use it for provisioning, you need to turn that on.

A source carries its own list of `features`, separate from the connector's. Your connector now
advertises `PROVISIONING`, because the spec declares `std:account:update`. Your source does not, and
a brand new source will not either. Sources are **read only** until somebody says otherwise.

Open your source, go to its **Configuration**, tick the option that **enables provisioning**, and
save.

That sets `enableProvisioningFeature` on the source and now you are ready to enable JIT.

### 5. Make the entitlement requestable

JIT governs assignments that arrive through the request process, so mark yours requestable.

Go to **Admin → Access Model → Entitlements**, find your entitlement, and choose **Actions → Edit**.
In the access request section, mark the entitlement
**requestable**, and save. Leave its approval settings empty.

Now get the entitlement's id in the tenant. This differs from the demo system's `grp_...`: the
`grp_...` is the value your source holds, and the tenant's id is what the JIT policy needs.

```bash
sail api get /entitlements/v1 \
  -q filters='value eq "grp_your_group_id"' \
  --jsonpath '$.*.id'
```

### 6. Put the entitlement under JIT policy

Until now you have built an ordinary requestable entitlement. This step changes what happens when
somebody is granted it.

Read the policy first. **You have to**, because there is one policy for the whole tenant and you are
adding to a list other people are also in:

```bash
sail api get /jit-activation-config/v1/policy \
  -H "X-SailPoint-Experimental:true" --pretty
```

```json
{
  "id": "6d38a587-302a-41d1-a3b1-ffae2c25c960",
  "entitlementIds": ["ae735f40-4de9-4163-801d-4a1444e59d35"],
  "maxActivationPeriodMins": 60,
  "maxActivationPeriodExtensionMins": 30,
  "defaultMaxActivationPeriodMins": 30,
  "defaultMaxActivationPeriodExtensionMins": 30,
  "notificationRecipients": [],
  "notificationTemplate": null,
  "applyToFutureAssignments": true
}
```

Paste that whole response here. The box reads the governed list out of it, adds your entitlement
from step 5, and builds the patch below:

<JitPolicyMerge />

```bash
sail api patch /jit-activation-config/v1/policy \
  -H "X-SailPoint-Experimental:true" \
  --body '[
    {"op": "replace", "path": "/entitlementIds", "value": your-merged-entitlement-ids},
    {"op": "replace", "path": "/applyToFutureAssignments", "value": true}
  ]'
```

:::danger Make sure not to overwrite the list!

`replace` overwrites the whole array, so every id already in `entitlementIds` has to appear in the
list you send. Dropping somebody else's id takes their entitlement out of JIT policy without warning
them, and their entitlement stops being activatable. Since there might be more than yourself using this 
tenant dropping that array could cause issues on someones hack.

:::


### 7. Get the assignment, without getting the access

#### First, check that requests do not need approval

Read the tenant's access request configuration:

```bash
sail api get /access-request-config/v1 --pretty
```

Look at `entitlementRequestConfig.grantRequestApprovalSchemes`. If it is already `null` or empty,
somebody has done this and you can go straight to requesting.

If it reads `sourceOwner`, it needs clearing. Out of the box, your request goes
to the source owner for approval, the source owner is you, and the platform will not let you approve
your own request. It reassigns the approval to a tenant administrator and we don't want to do that for this hack.

```bash
sail api put /access-request-config/v1 --body '{
  "approvalsMustBeExternal": false,
  "autoApprovalEnabled": false,
  "reauthorizationEnabled": false,
  "govGroupVisibilityEnabled": false,
  "fallbackAccessDurationInDays": null,
  "entitlementRequestConfig": {
    "allowEntitlementRequest": true,
    "requestCommentsRequired": false,
    "deniedCommentsRequired": false,
    "grantRequestApprovalSchemes": "",
    "revokeRequestApprovalSchemes": null
  },
  "requestOnBehalfOfConfig": {
    "allowRequestOnBehalfOfAnyoneByAnyone": true,
    "allowRequestOnBehalfOfEmployeeByManager": true,
    "allowRequestOnBehalfOfForMachineIdentity": true,
    "allowRequestForMachineByOwner": false
  },
  "approvalReminderAndEscalationConfig": {
    "daysUntilEscalation": null,
    "daysBetweenReminders": null,
    "maxReminders": null,
    "fallbackApproverRef": null
  }
}'
```

Read it back and `grantRequestApprovalSchemes` will be `null`. An empty string and `null` mean the
same thing here: no approval.

#### Then check you have an account on this source

JIT grants access by adding an entitlement to an account that already exists. If the identity has no
account on the source the entitlement came from, the platform tries to **create** one first, but our connector is not setup to handle that.

```bash
sail api get /accounts/v1 \
  -q filters='identityId eq "your-identity-id" and sourceId eq "your-source-id"' \
  --jsonpath '$.*.nativeIdentity'
```

You want your `usr_...` from step 2. An empty result means step 2's correlation did not land on this
source, so go back and fix it before requesting anything.

#### Request it

Request the entitlement for yourself in the **Request Center**. With the approval scheme cleared it
completes on its own, with nothing to approve.

Here is the part worth slowing down for. When the request completes, **you do not have the access.**

```bash
curl -s "https://dugfer5z7k.execute-api.us-east-1.amazonaws.com/v1/groups/grp_your_group_id/members" \
  -H "Authorization: Bearer sck_your_key_here"
```

Your account is not in the member list, and your connector log shows no `std:account:update`.
Nothing was provisioned, and that is correct.

What you hold instead is an **entitlement connection** of type `JIT`, a record saying you are
approved for this access and may turn it on. Standing access would have ended with the group on your
account. JIT ends with permission to grant yourself the group later.

:::tip

**Check:** the request is complete, and `/members` does **not** contain your account. If it does,
the entitlement was granted as standing access, so go back to step 6 and confirm your entitlement id
really is in `entitlementIds`.

:::

### 8. See it on Launchpad

Go to **MySailPoint → Launchpad → Just-In-Time Access**. Your entitlement is listed, with no access
granted and an option to activate it.

That is the finish line, and it is worth being clear about what it proves. A standing entitlement
would never appear on that page, because there would be nothing to activate — you would simply hold
it. Yours is sitting there waiting, which means the platform has accepted it as access you are
approved for but do not currently have. The split between the assignment and the activation, from
the top of this page, is now a real object in your tenant.

Confirm the same thing from the developer side:

```bash
sail api get /entitlement-connections/v1/current-identity \
  -q filters='type eq "JIT" and entitlement.value eq "grp_your_group_id"' \
  --pretty
```

```json
{
  "id": "6c692d9972f8400ca4560a68f62c4c5f",
  "identity": {"id": "...", "name": "hack.day"},
  "account": {"id": "...", "name": "yourname"},
  "entitlement": {"id": "...", "value": "grp_a1b2c3d4e5f6"},
  "source": {"id": "...", "name": "SaaS Connectivity Demo"},
  "state": {"value": "Available"},
  "type": "JIT",
  "jit": {}
}
```

`type` is `JIT` rather than `STANDING`. `state` reads `Available`, meaning ready to activate rather
than active. And `jit` is empty, because no activation has happened yet. Those three fields together
are the whole idea in one object.

:::tip

**You are done.** Show a developer advocate four things:

1. Your group in the demo system, with `memberCount: 0`. Nobody holds this access.
2. The entitlement in your tenant, carrying the permissions your connector reported.
3. The entitlement on **Launchpad → Just-In-Time Access**, awaiting activation.
4. `type: JIT` and `state: Available` on the connection.

Together those say: the access exists, it is approved for you, and it is not provisioned. That is

## What happens when you activate

You have built the hard half. The activation half runs entirely on the connector you wrote in step 3,
and it is worth understanding even if you do not run it today.

| Operation | What the platform does | What your connector is sent |
| --- | --- | --- |
| **Activate** | Opens a window, up to 30 minutes | `std:account:update`, `Add` on `groups` |
| **Extend** | Moves the expiry later | nothing — the access is already provisioned |
| **Deactivate** | Closes the window early | `std:account:update`, `Remove` on `groups` |
| **Expiry** | Closes the window on its own | `std:account:update`, `Remove` on `groups` |

The last row is the one that makes JIT worth having. Nobody files a ticket, nobody runs a job on
their laptop, and nobody clicks anything. The window ends and the platform calls your connector to
take the access back. Your `Revoked grp_... from usr_...` line appears in a log nobody was watching.

### If you have a few minutes spare

Activating costs about a minute, and it is the moment your own code provisions real access. Leave
`sail conn logs tail` running in a second terminal and send:

```bash
sail api post /jit-activations/v1/activate \
  -H "X-SailPoint-Experimental:true" \
  --body '{
    "connectionId": "your-connection-id-from-step-8",
    "activationPeriodMins": 30
  }'
```

You get `202 Accepted`, not `200`, because the activation runs as a workflow and the response only
says it started. Within a few seconds your log prints `Granted grp_... to usr_...`, and the group in
the demo system has a member for the first time:

```bash
curl -s "https://dugfer5z7k.execute-api.us-east-1.amazonaws.com/v1/groups/grp_your_group_id/members" \
  -H "Authorization: Bearer sck_your_key_here"
```

Then hand it straight back, and watch the same handler revoke it:

```bash
sail api post /jit-activations/v1/deactivate \
  -H "X-SailPoint-Experimental:true" \
  --body '{"connectionId": "your-connection-id-from-step-8"}'
```

Read the connection once more and `jit.activation`, `jit.provisioned`, `jit.deactivation` and
`jit.deprovision` all carry times, while `type` is still `JIT` and `state` is back to `Available`.
You are still approved for the access. You simply do not hold it. The assignment outlived the
activation, which is the point.

Activation moves through a sequence of states, and the names describe what is happening to your
connector: `CREATING`, `ACTIVATING`, `PROVISIONED` (your handler returned, the access is live),
`DEPROVISIONING`, `COMPLETED`. `INVALID` and `ERROR` mean validation failed or your connector threw,
and `REVOKED` means an administrator took the access away early.

## Stretch goals

- **Watch an activation expire properly.** Activate, note `jit.expiration`, and come back in half an
  hour. This is the only way to see the thing JIT is actually for: your connector revoking access
  with nobody having asked it to. Start it before you break for lunch.
- **Email somebody when privileged access turns on.** Build a workflow on the **Provisioning
  Completed** trigger, filter it to your source, and send mail when the payload's
  `attributeRequests` contains an `Add` on `groups`. The same workflow fires on expiry with a
  `Remove`, so one workflow reports both ends of the window.
  [Track 01](/hack-day/jit-workflows) builds the email step. Simpler alternative: put an address in
  the policy's `notificationRecipients`.
- **Report on standing access that should not be standing.** `GET /entitlement-connections/v1` with
  `filters=type eq "STANDING"` lists assignments nobody has to activate. Join it against
  `entitlement.privilegeLevel.effective` to find the privileged ones. That list is the business case
  for JIT, in one API call. To convert them, `POST /entitlement-connections/v1` takes up to 100
  `{connectionId, type}` pairs and switches assignments between `JIT` and `STANDING`.
