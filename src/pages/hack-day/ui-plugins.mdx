# Track 03 · UI Plugins

Put your own page inside the product. You will scaffold a UI plugin, register it in your tenant, and
then edit it on your laptop while the tenant renders your code live - no hosting to arrange.

A UI plugin is not a separate app that sits beside Identity Security Cloud (ISC). It is a
micro-frontend that ISC loads into one of its own slots, so your page runs inside the product and
uses the same user session. Every API call you write is already authenticated as the person looking at the screen.

The page you build is a manager lookup. Pick a manager from a searchable dropdown, and get a table of
every person who reports to them.

:::info Experimental feature

UI Plugins are experimental. The manifest format can still change, and your tenant must have the
feature switched on. If it is not, every backend command returns a "not enabled for this tenant"
error, so confirm this with a developer advocate in the room before you start.

:::

## What you are building

```
  sail ui-plugins init        sail ui-plugins create       sail ui-plugins link
  scaffold a workspace   ->   register it in the      ->   point the tenant at
  on your laptop              tenant and get an ID         your local dev server
                                                                     |
                                                                     v
                       +------------------------------------------------------+
                       | https://<tenant>/ui/plugin/<id>?spPluginDev=<alias>  |
                       |                                                      |
                       |  Manager  [ Jean Bartik                    x  v ]    |
                       |           52 managers · 1,204 identities loaded      |
                       |                                                      |
                       |  Direct reports (3)                                  |
                       |  NAME               EMAIL       DEPARTMENT   STATUS  |
                       |  (A) Ada Byron      ada@...     Engineering  ACTIVE  |
                       |  (G) Grace Hopper   grace@...   Engineering  ACTIVE  |
                       |  (M) Mary Jackson   mary@...    Engineering  ACTIVE  |
                       +------------------------------------------------------+
                                            ^
                                            |
                          Paginator.paginate(listIdentitiesV1)
                        pages through every identity on load. It
                        fills the dropdown and the table, and
                        nothing else hits the API again.
```

One API call does all of it, and the reason is worth knowing before you write it. Every identity
record carries a **reference** to its manager in the same way a database
row holds a foreign key rather than the whole related row. Read those references one way and you have
the list of managers for the dropdown. Read them the other way and you have each manager's reports. So
a single page of identities answers both halves of the question, with no second request.

#### Personal access token

The CLI acts on your behalf against your tenant's APIs, so it needs credentials. A personal access
token (PAT) is the simplest way to get authenticated.

- In your tenant, open **Preferences → Personal Access Tokens**, or go straight to
  `https://[tenant].identitynow.com/ui/d/user-preferences/personal-access-tokens`.
- Click **New Token** and give it a description, such as `hack-day-cli`.
- For the vendor integration, choose **Other / No associated vendor integration**.
- Leave the scopes list empty. An empty list means the token defaults to `sp:scopes:all` and inherits
  your own access, which is what the plugin commands need.
- Click **Create Token**, then copy the **Client ID** and **Client Secret**. The secret is never
  shown again.

More detail: [personal access tokens](/docs/api/authentication#generate-a-personal-access-token).

#### Point the CLI at your tenant

In your terminal, run these three commands one at a time. The first creates a named environment
pointing at your tenant, the second stores the PAT you just created, and the third tells the CLI to
authenticate with that PAT. You will be prompted for your tenant URL
(`https://[tenant].identitynow.com`) and API URL (`https://[tenant].api.identitynow.com`), then for
the client ID and secret from above.

**Your terminal**

```bash
sail env create hackday
sail set pat
sail set auth pat
```

More detail: [CLI install and configuration](/docs/tools/cli).

### 2. Scaffold the plugin workspace

In your terminal, paste these commands one at a time. `sail ui-plugins init` downloads the SailPoint
starter template and personalizes it in a new folder, `cd` moves you into it, and `npm install`
downloads its dependencies.

**Your terminal**

```bash
sail ui-plugins init manager-lookup
cd manager-lookup
npm install
```

What you just generated is a normal Angular application plus two files that belong to UI plugins.
Six files matter:

| File | What it does |
| --- | --- |
| `sp-ui-plugin.json` | Describes the plugin to ISC: its alias, its API scopes, and the slots it fills |
| `src/app/app.config.ts` | Wires up the SDK and the themed component library |
| `src/app/core/spds-prime-theme.ts` | The SailPoint design system, as a PrimeNG theme. Generated, and not yours to edit |
| `src/app/app.ts` | Your component, populated with some default examples |
| `src/app/app.html` | Your template |
| `src/app/app.scss` | Your styles (empty in the scaffold) |

Open `sp-ui-plugin.json` first, because it is the only one that is not ordinary Angular:

**`sp-ui-plugin.json`**

```json
{
    "version": 1,
    "manifest": {
        "alias": "manager-lookup",
        "name": { "en": "manager-lookup" },
        "description": { "en": "manager-lookup" },
        "apiScopes": ["sp:scopes:all"],
        "contentSecurityPolicies": {},
        "permissionPolicy": {},
        "iframeAllow": {},
        "state": "ENABLED",
        "slots": [{ "slotId": "full-page" }]
    },
    "build": {
        "outDir": "./dist/manager-lookup/browser",
        "port": 4200
    }
}
```

Two halves, and the split matters:

- **`manifest`** is the part sent to ISC. It declares the alias, the display name, the API scopes your
  page may use, and the **slots** the plugin occupies. `full-page` means your plugin gets a whole page
  of its own rather than a panel inside an existing screen.
- **`build`** never leaves your laptop. `outDir` tells `upload` where your compiled files land, and
  `port` is where `link` assumes your dev server listens.

You can check the manifest's structure at any time without touching the backend:

**Your terminal, in the `manager-lookup` folder**

```bash
sail ui-plugins validate-manifest
```

- [CLI command reference](https://developer.sailpoint.com/docs/ui-plugins/cli-command-reference)

### 3. Register the plugin instance

`create` reads `sp-ui-plugin.json`, validates it locally, and sends the `manifest` section to your
tenant to register a **plugin instance**. Nothing is deployed and no code is uploaded.

**Your terminal**

```bash
sail ui-plugins create
```

**Terminal output**

```text
Created plugin instance 033b32b5-280f-4d78-a856-05c2a34d15d1 (alias: manager-lookup)
```

Keep that ID. It appears in every URL you open from here on.


### 4. Load your local code in the tenant

Your plugin gets its API access from the page that hosts it. On startup it performs a handshake with
the ISC **App Shell**, and the App Shell hands back the tenant, the signed-in user, and the token that
API calls travel on. Open `https://localhost:4200` on its own and every API call fails with it. The page renders, but it has no data.

So you do not develop against `localhost`. You develop against your tenant, and `link` tells the
tenant to load your page from your dev server instead of from deployed files. The override is bound to
your own identity, so nobody else in the tenant is affected.

Start the dev server first. Use a **second terminal**, and leave it running:

**Your second terminal**

```bash
npm run start
```

Then link it, back in the first terminal:

**Your first terminal**

```bash
sail ui-plugins link
```

**Terminal output**

```text
Plugin manager-lookup linked to port 4200
To load your local plugin in ISC navigate to:
https://<tenant>/ui/plugin/033b32b5-280f-4d78-a856-05c2a34d15d1?spPluginDev=manager-lookup
```

Open the printed URL. You get the starter page rendered inside your tenant, with a **Local Dev** badge
on it. Edit a file, refresh the browser, and your changes are all there.

:::caution "Can't reach your local plugin server"

The dev server runs over HTTPS with a self-signed certificate, and your browser refuses it until you
say otherwise. This error almost always means one of two things:

- `npm run start` is not running.
- You have not accepted the certificate yet. Open `https://localhost:4200` in a new tab, accept the
  warning, then return to the ISC tab and click **Retry**. The browser will flag the dev server as
  **Not Secure**, which is expected for local development.

:::

### 5. Understanding Generated Files

The scaffold is a working Angular app, and most of it is boilerplate you can ignore. Three files are
worth reading before you change anything, because between them they explain why your code in the next
four steps is as short as it is, and why the page looks like ISC without you styling it.

**`src/app/core/sailpoint-plugin.service.ts`** owns the App Shell handshake. It creates the plugin SDK
exactly once, runs the handshake once, and exposes the result as signals you can read from anywhere:

| Signal | What it gives you |
| --- | --- |
| `context()` | Tenant, signed-in user, and current page. Null until the handshake finishes. |
| `status()` | `pending`, then either `ready` or `failed`. |
| `apiReady()` | True once API calls are safe to make. |
| `tenant()`, `user()` | Convenience slices of `context()`. |

You will not edit this file. You inject it and read those signals.

**`src/app/app.config.ts`** wires up three things, and all three are already done for you:

```ts
provideSailPoint(),
providePrimeNG({
  theme: {
    preset: spdsPrimePreset,
    options: { darkModeSelector: SPDS_DARK_MODE_SELECTOR, prefix: SPDS_THEME_PREFIX },
  },
}),
provideAppInitializer(async () => {
  await inject(SailpointPluginService).whenReady();
});
```

`provideSailPoint()` registers an HTTP interceptor that attaches the plugin's token to every SDK
request.

`provideAppInitializer()` awaits the handshake *before* Angular renders anything, so your first API
call cannot race it. Because of that line you can call the API from the moment your component exists.

`providePrimeNG()` is the third one. [PrimeNG](https://primeng.org/) is the component library SailPoint has picked for UI plugins, and the
scaffold arrives with it installed, themed, and configured. You write `<p-select>` and you get a
SailPoint-looking select.

**`src/app/core/spds-prime-theme.ts`** is the theme that `providePrimeNG()` is handed. It is six
thousand lines, it is generated, and the header tells you not to edit it. The only thing that is worth mentioning are the last two lines:

```ts
export const SPDS_DARK_MODE_SELECTOR = '.spds-dark';
export const SPDS_THEME_PREFIX = 'spds';
```

The prefix is important. PrimeNG publishes every design token in the theme as
a CSS variable, and the prefix decides their names. SailPoint's tokens are `--spds-text-color`,
`--spds-text-muted-color`, `--spds-content-border-color`, `--spds-primary-color`, and so on. Read those
in your own stylesheet instead of picking colours, and your page tracks the theme. It is also why
copying a PrimeNG example off the web can look wrong here: those examples assume the default `--p-`
prefix.

The theme brings two more things you get for free:

- **Typography.** It sets the page font and styles `h1` through `h6`, so headings need no CSS from you.
  It also ships `.spds-h1` to `.spds-h6` (and a `--semibold` variant of each) for when you want a
  heading's *look* on an element that is not that heading level.
- **Dark mode.** Everything has a dark variant already, switched by the `.spds-dark` class from that
  export. Nothing in this track turns it on, but it's worth knowing about it.

A future `@sailpoint/sds` package will replace this file with a published one, which is what the `TODO`
comment above `providePrimeNG()` is about.

**`src/app/app.ts` and `src/app/app.html`** are a demonstration, not a foundation. Open them and you
will see the pattern you are about to follow: PrimeNG components in the `imports` array, and a map from
a plugin state onto a `p-tag` severity. You replace both files in the next step.

- [PrimeNG components](https://primeng.org/select)
- [PrimeNG theming](https://primeng.org/theming)

### 6. List the identities

One load feeds this whole page: the dropdown, the reports table, and the count. Get it working on its
own before you build anything on top of it.

The Angular SDK is split by API partition, so the identities service comes from its own entry point,
and every method on it returns an Observable:

**`src/app/app.ts`**

```ts
import { IdentitiesService, type Identity } from '@sailpoint/angular-sdk/identities';
```

**Method:** `listIdentitiesV1()`, with one thing wrapped around it. A list endpoint returns at most
**250 records per request**, so a single call quietly truncates any tenant with more identities than that - and a
manager whose reports fall outside that first page would show up with none. The SDK ships a
`Paginator` for exactly this, so use it from the start rather than discovering the ceiling later:

**`src/app/app.ts`**

```ts
import { Paginator } from '@sailpoint/angular-sdk';
```

`Paginator.paginate()` runs the paging loop for you and emits once with every record collected:

**`src/app/app.ts`, inside `loadIdentities()`**

```ts
Paginator.paginate(
  (params) => this.identitiesSvc.listIdentitiesV1(params),
  { sorters: 'name' },
);
```

It takes three arguments. The first is a function that calls the list method. The second is the base parameters, and anything the endpoint
accepts can go here; `sorters: 'name'` gets the dropdown back alphabetical without you sorting it.
The third argument is the page size, which defaults to 250.

`firstValueFrom()` then turns that Observable into a promise, which reads better in a method that
loads once and stores the result.

Replace the entire contents of `src/app/app.ts` with the shell below. It injects the plugin service
and the identities service, declares the three signals the page runs on, and starts the load from an
`effect()` that waits for `apiReady()`.

The load itself is commented out inside `loadIdentities()`. Uncomment it. It is the only thing you
have to do in this step, and it is commented rather than missing so that you get a better understanding of where key edits take place.

That `effect()` is doing real work, so it is worth a look while you are in there. An effect re-runs
whenever a signal it reads changes, and it reads `apiReady()` so the moment the handshake flips to
ready, the load starts.

The two PrimeNG modules in `imports` follow the same pattern the starter file used. A standalone
Angular component has to declare every component its template uses, so this array grows in each of the
next two steps.

**`src/app/app.ts`**

```ts
import { Component, effect, inject, signal } from '@angular/core';
import { SailpointPluginService } from '@core';
import { Paginator } from '@sailpoint/angular-sdk';
import { IdentitiesService, type Identity } from '@sailpoint/angular-sdk/identities';
import { MessageModule } from 'primeng/message';
import { TagModule } from 'primeng/tag';
import { firstValueFrom } from 'rxjs';

@Component({
  selector: 'app-root',
  imports: [MessageModule, TagModule],
  providers: [IdentitiesService],
  templateUrl: './app.html',
  styleUrl: './app.scss',
})
export class App {
  protected readonly plugin = inject(SailpointPluginService);
  private readonly identitiesSvc = inject(IdentitiesService);

  /** Every identity the page has loaded. Everything else is derived from this. */
  protected readonly identities = signal<Identity[]>([]);
  protected readonly loading = signal(false);
  protected readonly error = signal('');

  private requested = false;

  constructor() {
    // Wait for the App Shell handshake, then load once.
    effect(() => {
      if (this.plugin.apiReady() && !this.requested) {
        this.requested = true;
        void this.loadIdentities();
      }
    });
  }

  protected async loadIdentities(): Promise<void> {
    this.loading.set(true);
    this.error.set('');

    try {
      // Paginator.paginate() walks the endpoint 250 records at a time and emits once
      // with every identity in the tenant. Uncomment it:
      // const identities = await firstValueFrom(
      //   Paginator.paginate(
      //     (params) => this.identitiesSvc.listIdentitiesV1(params),
      //     { sorters: 'name' },
      //   ),
      // );
      // this.identities.set(identities);
    } catch (err) {
      this.error.set(this.formatApiError(err));
    } finally {
      this.loading.set(false);
    }
  }

  private formatApiError(err: unknown): string {
    return err instanceof Error ? `${err.name}: ${err.message}` : String(err);
  }
}
```

```ts
import { Component, effect, inject, signal } from '@angular/core';
import { SailpointPluginService } from '@core';
import { Paginator } from '@sailpoint/angular-sdk';
import { IdentitiesService, type Identity } from '@sailpoint/angular-sdk/identities';
import { MessageModule } from 'primeng/message';
import { TagModule } from 'primeng/tag';
import { firstValueFrom } from 'rxjs';

@Component({
  selector: 'app-root',
  imports: [MessageModule, TagModule],
  providers: [IdentitiesService],
  templateUrl: './app.html',
  styleUrl: './app.scss',
})
export class App {
  protected readonly plugin = inject(SailpointPluginService);
  private readonly identitiesSvc = inject(IdentitiesService);

  /** Every identity the page has loaded. Everything else is derived from this. */
  protected readonly identities = signal<Identity[]>([]);
  protected readonly loading = signal(false);
  protected readonly error = signal('');

  private requested = false;

  constructor() {

    effect(() => {
      if (this.plugin.apiReady() && !this.requested) {
        this.requested = true;
        void this.loadIdentities();
      }
    });
  }

  protected async loadIdentities(): Promise<void> {
    this.loading.set(true);
    this.error.set('');

    try {
```

Four of those attributes are worth noting `<select>`:

| Attribute | What it buys you |
| --- | --- |
| `[filter]="true"` | A search box inside the dropdown to handle tenants with many managers |
| `[showClear]="true"` | An × to clear the selection, so the user can get back to no filter. |
| `emptyMessage` | What to show when `managers()` is empty, instead of a blank panel. |

One detail in that binding is deliberate: `[ngModel]` is one-way, not the usual `[(ngModel)]`. The
signal is the single source of truth for what is selected, so the value flows out of the signal into
the control, and the control reports changes back through `(onChange)`. Binding both ways would give
you two places holding the same state.

Note the `?.` in that line. `managerRef` is nullable, because the people at the top of the

The table wants three small helpers, so add these below `onManagerChange()`.

The first reads a named attribute off an identity. Department is not a top-level field: it lives in
`attributes`, which the SDK types as a plain `object` because its contents differ from tenant to
tenant. The second turns a name into initials for an avatar. The third maps an identity status onto a
PrimeNG severity, which is what makes the status colour mean something instead of being decoration:

**`src/app/app.ts`, inside the `App` class, below `onManagerChange()`**

```ts
  /** Reads one identity attribute out of the untyped attributes map. */
  protected attr(identity: Identity, key: string): string {
    const attributes = identity.attributes as Record<string, unknown> | undefined;
    const value = attributes?.[key];
    return typeof value === 'string' && value ? value : '-';
  }

  /** Initials for the avatar, so "Jean Bartik" becomes "JB". */
  protected initials(name: string): string {
    return name
      .split(' ')
      .filter(Boolean)
      .slice(0, 2)
      .map((part) => part[0].toUpperCase())
      .join('');
  }

  /** Maps an identity status onto a p-tag severity, so the colour carries meaning. */
  protected statusSeverity(status: string | undefined): 'success' | 'warn' | 'danger' | 'secondary' {
    switch (status) {
      case 'ACTIVE':
      case 'REGISTERED':
        return 'success';
      case 'PENDING':
      case 'WARNING':
      case 'LOCKED':
        return 'warn';
      case 'DISABLED':
      case 'TERMINATED':
      case 'DEACTIVATED':
      case 'ERROR':
        return 'danger';
      default:
        return 'secondary';
    }
  }
```

### 9. Deploy to your tenant

:::tip Short on time?

This step is optional. Everything above already works, and you can show a developer advocate the page running in
your tenant with the **Local Dev** badge on it.

:::

Everything so far has run on your laptop. These commands put the compiled page in your tenant.

```bash
npm run build
sail ui-plugins upload
```

**Terminal output**

```text

The plugin can be viewed at:
https://<tenant>/ui/plugin/033b32b5-280f-4d78-a856-05c2a34d15d1
```

`upload` is a deploy step, not a build step. It uploads whatever is already in `build.outDir` and
never runs your framework's build for you.

The build prints two numbers and one complaint. Expect all three:

**Terminal output**

```text
Initial chunk files | Names | Raw size | Estimated transfer size
main-NGW7B3FQ.js    | main  |  1.08 MB |               209.13 kB

▲ [WARNING] bundle initial exceeded maximum budget. Budget 500.00 kB was not met by 584.57 kB
```

The raw bundle lands around 1 MB and
trips the scaffold's 500 kB budget warning. That is a **warning**, not an error: the build completes
and `upload` works.

The number that matters is the one on the right. What a browser downloads is the compressed figure,
about 210 kB, which is ordinary for a single-page app.

Open the printed URL. It is the same page without the **Local Dev** badge, because the tenant is
serving the uploaded files rather than your dev server.

The alias is the lookup key, and the CLI resolves it against whichever tenant you are authenticated
to. The identical `upload` command deploys to staging or to production depending only on
`sail env`. There are no environment-specific plugin IDs to track.

### 10. Stretch goals

Pick whichever looks most interesting. Each one maps to something real plugins actually have to do.

- **Show the manager, not just the reports.** Your page knows a `managerRef` and nothing else about the person you selected. No email, no department, no title. Those live
  on the manager's own identity record, so getting them means a second call
- **Add a name filter.** Put a text input above the dropdown and narrow the reports table as the user
  types. Do it as a third `computed()` reading a signal from the input.
- **Show the whole chain.** Once you have that second lookup working, notice that the manager has a
  `managerRef` too. Follow it upward with repeated `getIdentityV1` calls and render the reporting line
  from the selected person to the top of the organization. Stop when `managerRef` is null.
- **Stream the pages instead of collecting them.** `Paginator.paginate()` holds every record in
  memory and emits once at the end, which is fine for a few thousand identities and wasteful for a
  hundred thousand. Swap it for `Paginator.paginatePages()`, which emits each page as it arrives.
- **Ask the server instead.** Replace the client-side filter with a real query. The search API can
  filter on manager, which `listIdentitiesV1` cannot.
- **Count them instead of listing them.** Use `searchAggregateV1` to get reports-per-manager for the
  whole tenant in one call and render it as a list. That is one request for a page that would otherwise
  take hundreds.
- **Reach for more of PrimeNG.** The library is large and you have used six components of it. Add
  `p-toast` so a failed lookup raises a notification instead of a line of text, swap the manager
  `p-select` for a `p-autocomplete` that searches the API as you type, or put the whole page behind
  `p-tabs` and add a second view. Every component is documented with a live example at
  [primeng.org](https://primeng.org/), and every one arrives themed.
- **Find the tokens you are not using.** Every design token in `spds-prime-theme.ts` is available to
  your CSS as `--spds-<token-path>`. Open your browser's dev tools, inspect any element the theme
  styled, and read the variables it resolved. It is the fastest way to learn what is available without
  reading six thousand generated lines.
