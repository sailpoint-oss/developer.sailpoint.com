# Track 03 · UI Plugins

Put your own page inside the product. You will scaffold a UI plugin, register it in your tenant, and
then edit it on your laptop while the tenant renders your code live - no hosting to arrange.

A UI plugin is not a separate app that sits beside Identity Security Cloud (ISC). It is a
micro-frontend that ISC loads into one of its own slots, so your page runs inside the product and
uses the same user session. Every API call you write is already authenticated as the person looking at the screen.

The page you build is a manager lookup. Pick a manager from a dropdown, and get that manager's details
plus every person who reports to them.

:::info Experimental feature

UI Plugins are experimental. The `sail ui-plugins` command group is hidden until you enable it, the
manifest format can still change, and your tenant must have the feature switched on. If it is not,
every backend command returns a "not enabled for this tenant" error — so confirm this with a developer
advocate in the room before you start.

:::

```
                                  |                          |
                       listIdentitiesV1()           getIdentityV1(managerId)
                       one call on load — fills      one call per selection —
                       the dropdown and the table    fills the manager card
```

Two API calls, and the second one exists for a reason worth knowing before you write it. An identity
record does not contain its manager — it contains a **reference** to the manager, an id and a display
name, in the same way a database row holds a foreign key rather than the whole related row. The
dropdown can be built from those references alone. The manager's email address cannot, because a
reference does not carry it. Somebody has to go and fetch that second person.

#### Personal access token

The CLI acts on your behalf against your tenant's APIs, so it needs credentials. A personal access
token (PAT) is the simplest way to get authenticated.

- In your tenant, open **Preferences → Personal Access Tokens**, or go straight to
  `https://[tenant].identitynow.com/ui/d/user-preferences/personal-access-tokens`.
- Click **New Token** and give it a description, such as `hack-day-cli`.
- For the vendor integration, choose **Other / No associated vendor integration**.
- Leave the scopes list empty. An empty list means the token defaults to `sp:scopes:all` and inherits
  your own access, which is what the plugin commands need — pick narrower scopes and they will fail
  with a `403`.
- Click **Create Token**, then copy the **Client ID** and **Client Secret**. The secret is never
  shown again.

More detail: [personal access tokens](/docs/api/authentication#generate-a-personal-access-token).

#### Point the CLI at your tenant

In your terminal, run these three commands one at a time. The first creates a named environment
pointing at your tenant, the second stores the PAT you just created, and the third tells the CLI to
authenticate with that PAT. You will be prompted for your tenant URL
(`https://[tenant].identitynow.com`) and API URL (`https://[tenant].api.identitynow.com`), then for
the client ID and secret from above.

```bash
sail env create hackday
sail set pat
sail set auth pat
```

More detail: [CLI install and configuration](/docs/tools/cli).

### 2. Scaffold the plugin workspace

In your terminal, paste these commands one at a time. `sail ui-plugins init` downloads the SailPoint
starter template and personalizes it in a new folder, `cd` moves you into it, and `npm install`
downloads its dependencies.

```bash
sail ui-plugins init
cd manager-lookup
npm install
```

`init` prompts for two things: a display name and a tenant-unique **alias**. Use `manager-lookup` for
both, and the new folder is named after the alias.

```text
Plugin Name: manager-lookup
Plugin Alias [manager-lookup]:

Created plugin workspace "manager-lookup".
```

What you just generated is a normal Angular application plus one file that belongs to UI plugins.
Four files matter:

| File | What it does |
| --- | --- |
| `sp-ui-plugin.json` | Describes the plugin to ISC: its alias, its API scopes, and the slots it fills |
| `src/app/app.ts` | Your component — the state and the API calls |
| `src/app/app.html` | Your template |
| `src/app/app.scss` | Your styles (empty in the scaffold) |

Open `sp-ui-plugin.json` first, because it is the only one that is not ordinary Angular:

```json
{
    "version": 1,
    "manifest": {
        "alias": "manager-lookup",
        "name": { "en": "manager-lookup" },
        "description": { "en": "manager-lookup" },
        "apiScopes": ["sp:scopes:all"],
        "contentSecurityPolicies": {},
        "permissionPolicy": {},
        "iframeAllow": {},
        "state": "ENABLED",
        "slots": [{ "slotId": "full-page" }]
    },
    "build": {
        "outDir": "./dist/manager-lookup/browser",
        "port": 4200
    }
}
```

Two halves, and the split matters:

- **`manifest`** is the part sent to ISC. It declares the alias, the display name, the API scopes your
  page may use, and the **slots** the plugin occupies. `full-page` means your plugin gets a whole page
  of its own rather than a panel inside an existing screen.
- **`build`** never leaves your laptop. `outDir` tells `upload` where your compiled files land, and
  `port` is where `link` assumes your dev server listens.

You can check the manifest's structure at any time without touching the backend:

```bash
sail ui-plugins validate-manifest
```

- [CLI command reference](https://d25wvbnzdj80l0.cloudfront.net/docs/ui-plugins/cli-command-reference)

### 3. Register the plugin instance

`create` reads `sp-ui-plugin.json`, validates it locally, and sends the `manifest` section to your
tenant to register a **plugin instance**. Nothing is deployed and no code is uploaded — you are
reserving the alias and getting an ID back.

```bash
sail ui-plugins create
```

```text
Created plugin instance 033b32b5-280f-4d78-a856-05c2a34d15d1 (alias: manager-lookup)
```

Keep that ID. It appears in every URL you open from here on.


### 4. Load your local code in the tenant

Your plugin gets its API access from the page that hosts it. On startup it performs a handshake with
the ISC **App Shell**, and the App Shell hands back the tenant, the signed-in user, and the token that
API calls travel on. Open `https://localhost:4200` on its own and there is no App Shell to talk to —
the handshake fails, and every API call fails with it. The page renders, but it has no data.

So you do not develop against `localhost`. You develop against your tenant, and `link` tells the
tenant to load your page from your dev server instead of from deployed files. The override is bound to
your own identity, so nobody else in the tenant is affected.

Start the dev server first. Use a **second terminal**, and leave it running:

```bash
npm run start
```

Then link it, back in the first terminal:

```bash
sail ui-plugins link
```

```text
Plugin manager-lookup linked to port 4200
To load your local plugin in ISC navigate to:
https://<tenant>/ui/plugin/033b32b5-280f-4d78-a856-05c2a34d15d1?spPluginDev=manager-lookup
```

Open the printed URL. You get the starter page rendered inside your tenant, with a **Local Dev** badge
on it. Edit a file, refresh the browser, and your change is there — that is your loop for the rest of
this track.

:::caution "Can't reach your local plugin server"

The dev server runs over HTTPS with a self-signed certificate, and your browser refuses it until you
say otherwise. This error almost always means one of two things:

- `npm run start` is not running — check the second terminal.
- You have not accepted the certificate yet. Open `https://localhost:4200` in a new tab, accept the
  warning, then return to the ISC tab and click **Retry**. The browser will flag the dev server as
  **Not Secure**, which is expected for local development.

:::

### 5. Read the files you did not write

The scaffold is a working Angular app, and most of it is boilerplate you can ignore. Two files are
worth reading before you change anything, because together they explain why your code in the next
four steps is as short as it is.

**`src/app/core/sailpoint-plugin.service.ts`** owns the App Shell handshake. It creates the plugin SDK
exactly once, runs the handshake once, and exposes the result as signals you can read from anywhere:

| Signal | What it gives you |
| --- | --- |
| `context()` | Tenant, signed-in user, and current page. Null until the handshake finishes. |
| `status()` | `pending`, then either `ready` or `failed`. |
| `apiReady()` | True once API calls are safe to make. |
| `tenant()`, `user()` | Convenience slices of `context()`. |

You will not edit this file. You inject it and read those signals.

**`src/app/app.config.ts`** contains two lines:

```ts
provideSailPoint(),
provideAppInitializer(async () => {
  await inject(SailpointPluginService).whenReady();
});
```

`provideSailPoint()` registers an HTTP interceptor that attaches the plugin's token to every SDK
request — which is why nothing you write from here mentions a token, a base URL, or a tenant name. The
initializer then awaits the handshake *before* Angular renders anything, so your first API call cannot
race it. Because of that second line you can call the API from the moment your component exists.

**`src/app/app.ts` and `src/app/app.html`** are a demonstration, not a foundation — the starter
template says so itself. You replace both of them in the next step.

### 6. List the identities

One API call feeds this whole page: the dropdown, the reports table, and the count. Get it working on
its own before you build anything on top of it.

The Angular SDK is split by API partition, so the identities service comes from its own entry point,
and every method on it returns an Observable:

```ts
import { IdentitiesService, type Identity } from '@sailpoint/angular-sdk/identities';
```

**Method:** `listIdentitiesV1()`. Two parameters are worth passing — `limit: 250` to get a useful page
rather than the default handful, and `sorters: 'name'` so the dropdown comes back alphabetical without
you sorting it. `firstValueFrom()` turns the Observable into a promise, which reads better in a method
that loads once and stores the result.

Replace the entire contents of `src/app/app.ts` with the shell below. It injects the plugin service
and the identities service, declares the three signals the page runs on, and starts the load from an
`effect()` that waits for `apiReady()` — so the data is on its way before the user touches anything.
That leaves you one line to write inside `loadIdentities()`: await the call, and pass what comes back
to `this.identities.set()`.

```ts
import { Component, effect, inject, signal } from '@angular/core';
import { SailpointPluginService } from '@core';
import { IdentitiesService, type Identity } from '@sailpoint/angular-sdk/identities';
import { firstValueFrom } from 'rxjs';

@Component({
  selector: 'app-root',
  imports: [],
  providers: [IdentitiesService],
  templateUrl: './app.html',
  styleUrl: './app.scss',
})
export class App {
  protected readonly plugin = inject(SailpointPluginService);
  private readonly identitiesSvc = inject(IdentitiesService);

  /** Every identity the page has loaded. Everything else is derived from this. */
  protected readonly identities = signal<Identity[]>([]);
  protected readonly loading = signal(false);
  protected readonly error = signal('');

  private requested = false;

  constructor() {
    // Wait for the App Shell handshake, then load once.
    effect(() => {
      if (this.plugin.apiReady() && !this.requested) {
        this.requested = true;
        void this.loadIdentities();
      }
    });
  }

  protected async loadIdentities(): Promise<void> {
    this.loading.set(true);
    this.error.set('');

    try {
      // call listIdentitiesV1 with limit and sorters, then pass the
      // result to this.identities.set()
    } catch (err) {
      this.error.set(this.formatApiError(err));
    } finally {
      this.loading.set(false);
    }
  }

  private formatApiError(err: unknown): string {
    return err instanceof Error ? `${err.name}: ${err.message}` : String(err);
  }
}
```

Then replace `src/app/app.html` with a template that prints the count and nothing else. It reads
`context()` for the tenant and user, so you can see the handshake worked, and it reports the states the
page can be in:

```html
<main>
  <header>
    <h1>Who reports to whom?</h1>
    @if (plugin.context(); as ctx) {
      <p class="muted">Tenant {{ ctx.tenant.org }} · signed in as {{ ctx.user.displayName }}</p>
    }
  </header>

  <section>
    @if (plugin.status() === 'failed') {
      <p class="error">
        The App Shell handshake did not complete, so this plugin has no API token. Open the
        <code>?spPluginDev=</code> URL that <code>sail ui-plugins link</code> printed.
      </p>
    } @else if (loading()) {
      <p class="muted">Loading identities…</p>
    } @else if (error()) {
      <p class="error">{{ error() }}</p>
    } @else {
      <p>Loaded {{ identities().length }} identities.</p>
    }
  </section>
</main>
```

Save both files. The dev server rebuilds on its own, so refresh the `?spPluginDev=` tab. You should
get your tenant and user name in the header, and a line like this:

```text
Loaded 47 identities.
```

If it says `Loaded 0 identities.`, the call returned but you dropped the result — check that
`this.identities.set()` actually runs.

### 7. Build the manager dropdown

Now turn those identities into a list of managers. There is an obvious way to do this that does not
work, and knowing why is most of the value in this step.

`listIdentitiesV1` cannot filter by manager. Its filterable fields are `id`, `name`, `alias`,
`firstname`, `lastname`, `email`, `cloudStatus`, `processingState`, `correlated`, and `protected` —
that is the whole list. So you do not ask the API for managers; you read them out of the identities you
already have. Every identity carries a `managerRef`, so the distinct set of those references **is** the
list of managers in your tenant.

There is an `isManager` flag on the identity record too, and deriving from the references instead has
one practical advantage: every option in your dropdown is guaranteed to return at least one result,
because it got there by being somebody's manager.

Add the `computed()` below to `app.ts`, above `private requested = false`, then write the one missing
line in the loop: put each `managerRef` into `byId`, keyed by `ref.id`. A `Map` does the
de-duplication for you, because one manager appears on every one of their reports.

```ts
  /**
   * The dropdown options. Every identity carries a managerRef, so the set of
   * managers is the set of distinct managerRef values in the loaded list.
   */
  protected readonly managers = computed<ManagerOption[]>(() => {
    const byId = new Map<string, ManagerOption>();

    for (const identity of this.identities()) {
      const ref = identity.managerRef;
      if (ref?.id && ref.name) {
        // add { id: ref.id, name: ref.name } to byId, keyed by ref.id
      }
    }

    return [...byId.values()].sort((a, b) => a.name.localeCompare(b.name));
  });
```

That needs two things the file does not have yet. Add `computed` to the existing import from
`@angular/core`, and declare the option shape above the `@Component` block:

```ts
/** One entry in the manager dropdown. */
interface ManagerOption {
  id: string;
  name: string;
}
```

Then swap the count in `app.html` for a real control. The `@for` block needs a `track` expression so
Angular can tell the options apart, and `option.id` is the natural key:

```html
    <label for="manager">Manager</label>
    <select id="manager" [disabled]="loading()">
      <option value="">{{ loading() ? 'Loading identities…' : 'Select a manager' }}</option>
      @for (option of managers(); track option.id) {
        <option [value]="option.id">{{ option.name }}</option>
      }
    </select>
```

Save and refresh. You should get a dropdown listing every manager in the tenant, alphabetically, with
each name appearing exactly once — if a name repeats, your `Map` is being keyed by something that is
not the manager's id.

### 8. Show the direct reports

Selecting a manager should list their reports, and you already have the data to do it — the same
`managerRef` that built the dropdown points the other way too. This step needs no API call at all.

Two pieces. First, somewhere to keep the selection, and a handler to fill it. Add the signal above the
`managers` computed:

```ts
  /** The manager the user picked in the dropdown. */
  protected readonly selectedManagerId = signal('');
```

And the handler at the bottom of the class, above `formatApiError()`. A native `change` event gives you
an untyped `EventTarget`, so cast it to read the value:

```ts
  /** Runs when the user picks a manager in the dropdown. */
  protected onManagerChange(event: Event): void {
    this.selectedManagerId.set((event.target as HTMLSelectElement).value);
  }
```

Second, the reports themselves, as another `computed()` below `managers`. Write the missing return: the
identities whose `managerRef.id` matches the selected id. The empty-string guard matters, because
"Select a manager" is a real option and must not match anybody:

```ts
  /** The direct reports of the selected manager. */
  protected readonly reports = computed<Identity[]>(() => {
    const managerId = this.selectedManagerId();
    if (!managerId) {
      return [];
    }
    // return the identities whose managerRef.id is managerId
  });
```

Now wire the dropdown to the handler by binding `(change)` on the existing `<select>`:

```html
    <select id="manager" (change)="onManagerChange($event)" [disabled]="loading()">
```

And add the table after the dropdown's closing `</section>`, still inside `<main>`:

```html
  @if (selectedManagerId()) {
    <section>
      <h2>Direct reports ({{ reports().length }})</h2>
      @if (reports().length === 0) {
        <p class="muted">This manager has no direct reports in the loaded identities.</p>
      } @else {
        <table>
          <thead>
            <tr>
              <th>Name</th>
              <th>Email</th>
              <th>Status</th>
            </tr>
          </thead>
          <tbody>
            @for (person of reports(); track person.id) {
              <tr>
                <td>{{ person.name }}</td>
                <td>{{ person.emailAddress || '—' }}</td>
                <td>{{ person.identityStatus || '—' }}</td>
              </tr>
            }
          </tbody>
        </table>
      }
    </section>
```

### 9. Fetch the selected manager

The table tells you who reports to the selected manager. It tells you almost nothing about the manager,
because all you have is a `managerRef` — an id and a display name. No email address, no department, no
title. Those live on the manager's own identity record, and getting them means a second call.

**Method:** `getIdentityV1()`. It takes one id and returns one full `Identity`.

This is the same two-lookup shape you meet everywhere in identity work: the first call tells you who
points at whom, and the second tells you about the person being pointed at.

```ts
import { Component, computed, effect, inject, signal } from '@angular/core';
import { SailpointPluginService } from '@core';
import { IdentitiesService, type Identity } from '@sailpoint/angular-sdk/identities';
import { firstValueFrom } from 'rxjs';

/** One entry in the manager dropdown. */
interface ManagerOption {
  id: string;
  name: string;
}

@Component({
  selector: 'app-root',
  imports: [],
  providers: [IdentitiesService],
  templateUrl: './app.html',
  styleUrl: './app.scss',
})
export class App {
  protected readonly plugin = inject(SailpointPluginService);
  private readonly identitiesSvc = inject(IdentitiesService);

  /** Every identity the page has loaded. Everything else is derived from this. */
  protected readonly identities = signal<Identity[]>([]);
  protected readonly loading = signal(false);
  protected readonly error = signal('');

  /** The manager the user picked, and that manager's own full record. */
  protected readonly selectedManagerId = signal('');
  protected readonly manager = signal<Identity | undefined>(undefined);
  protected readonly managerLoading = signal(false);

  /**
   * The dropdown options. Every identity carries a managerRef, so the set of
   * managers is the set of distinct managerRef values in the loaded list.
   */
  protected readonly managers = computed<ManagerOption[]>(() => {
    const byId = new Map<string, ManagerOption>();

    for (const identity of this.identities()) {
      const ref = identity.managerRef;
      if (ref?.id && ref.name) {
        byId.set(ref.id, { id: ref.id, name: ref.name });
      }
    }

    return [...byId.values()].sort((a, b) => a.name.localeCompare(b.name));
  });

  /** The direct reports of the selected manager. */
  protected readonly reports = computed<Identity[]>(() => {
    const managerId = this.selectedManagerId();
    if (!managerId) {
      return [];
    }
    return this.identities().filter((identity) => identity.managerRef?.id === managerId);
  });

  private requested = false;

  constructor() {
    // Wait for the App Shell handshake, then load once.
    effect(() => {
      if (this.plugin.apiReady() && !this.requested) {
        this.requested = true;
        void this.loadIdentities();
      }
    });
  }

  protected async loadIdentities(): Promise<void> {
    this.loading.set(true);
    this.error.set('');

    try {
      const identities = await firstValueFrom(
        this.identitiesSvc.listIdentitiesV1({ limit: 250, sorters: 'name' }),
      );
      this.identities.set(identities);
    } catch (err) {
      this.error.set(this.formatApiError(err));
    } finally {
      this.loading.set(false);
    }
  }

  /** Runs when the user picks a manager in the dropdown. */
  protected async onManagerChange(event: Event): Promise<void> {
    const managerId = (event.target as HTMLSelectElement).value;
    this.selectedManagerId.set(managerId);
    this.manager.set(undefined);

    if (!managerId) {
      return;
    }

    // Second API call: a managerRef holds only an id and a name, so the
    // manager's email and attributes need their own lookup.
    this.managerLoading.set(true);

    try {
      const manager = await firstValueFrom(this.identitiesSvc.getIdentityV1({ id: managerId }));
      this.manager.set(manager);
    } catch (err) {
      this.error.set(this.formatApiError(err));
    } finally {
      this.managerLoading.set(false);
    }
  }

  /** Reads one identity attribute out of the untyped attributes map. */
  protected attr(identity: Identity, key: string): string {
    const attributes = identity.attributes as Record<string, unknown> | undefined;
    const value = attributes?.[key];
    return typeof value === 'string' && value ? value : '—';
  }

  private formatApiError(err: unknown): string {
    return err instanceof Error ? `${err.name}: ${err.message}` : String(err);
  }
}
```

Everything so far has run on your laptop. These commands put the compiled page in your tenant, so it

second uploads the result.

```bash
npm run build

```

```text

The plugin can be viewed at:
https://<tenant>/ui/plugin/033b32b5-280f-4d78-a856-05c2a34d15d1
```

`upload` is a deploy step, not a build step — it uploads whatever is already in `build.outDir` and
never runs your framework's build for you. Skip `npm run build` and it fails immediately:

```text
Error: output directory ./dist/manager-lookup/browser does not exist
```

Open the printed URL. It is the same page without the **Local Dev** badge, because the tenant is
serving the uploaded files rather than your dev server. Run `sail ui-plugins unlink` to drop your
override and confirm the deployed copy stands on its own.

The alias is the lookup key, and the CLI resolves it against whichever tenant you are authenticated
to — so the identical `upload` command deploys to staging or to production depending only on
`sail env`. There are no environment-specific plugin IDs to track.

### 11. Stretch goals

Pick whichever looks most interesting. Each one maps to something real plugins actually have to do.

- **Add a name filter.** Put a text input above the dropdown and narrow the reports table as the user
  types. Do it as a third `computed()` reading a signal from the input — no API call needed.
- **Show the whole chain.** The manager has a `managerRef` too. Follow it upward with repeated
  `getIdentityV1` calls and render the reporting line from the selected person to the top of the
  organization. Stop when `managerRef` is null, and stop if you see an id twice — real data is not
  always a tree.
- **Fix the 250 limit.** The page loads one page of identities, so a large tenant is silently
  truncated. Either page through with `limit` and `offset` until a short page comes back, or pass
  `count: true` and read the `X-Total-Count` header first by calling with `observe: 'response'`.
- **Ask the server instead.** Replace the client-side filter with a real query. The search API can
  filter on manager, which `listIdentitiesV1` cannot:

  ```ts
  import { SearchService, Index } from '@sailpoint/angular-sdk/search';

  const results = await firstValueFrom(
    this.searchSvc.searchPostV1({
      search: {
        indices: [Index.Identities],
        query: { query: `manager.id:${managerId}` },
        sort: ['name'],
      },
      limit: 250,
    }),
  );
  ```

  Be ready for one surprise: `searchPostV1` returns search documents, not `Identity` objects, so the
  field names differ. Log one result and fix the table columns before you fight the types.
- **Count them instead of listing them.** Use `searchAggregateV1` to get reports-per-manager for the
  whole tenant in one call and render it as a list. That is one request for a page that would otherwise
  take hundreds.
- **Fill a different slot.** Change `slots` in `sp-ui-plugin.json`, then `create` a second plugin
  instance and see where it lands in the product. `full-page` is what the starter uses, and it is not
  the only one.
